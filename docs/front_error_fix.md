# Серега, что нужно исправить во фронтенде

Серега, backend теперь использует JWT и отдаёт авторов, курсы и уроки через API. Ниже — конкретные изменения, чтобы React-клиент работал с Django по одному контракту.

## 1. Переключение с mock на API

Сейчас `src/services/index.js` переключает одним флагом сразу авторизацию, каталог и оплату. Реального API оплаты пока нет — это отдельный будущий этап. Если просто поставить `VITE_USE_MOCK=false`, фронтенд начнёт вызывать отсутствующие `/payments/` и `/me/purchases/`.

Раздели выбор источника по сервисам: включи Django для `authService` и `catalogService`, а `paymentService` пока оставь mock. Добавь для этого отдельные переменные окружения и укажи их в `src/config.js`/`src/services/index.js`. Например, для локальной разработки:

```env
VITE_API_URL=/api
VITE_USE_API_AUTH=true
VITE_USE_API_CATALOG=true
VITE_USE_API_PAYMENT=false
```

После этого `npm run dev` использует настроенный в `vite.config.js` proxy `/api` → `http://localhost:8000`. В браузере базовый адрес останется `/api`.

## 2. Вход по имени и телефону с JWT

Backend требует имя при запросе SMS. Сейчас форма `PhoneAuthForm` спрашивает только телефон. Добавь поле имени и сохраняй его в состоянии формы. Правила имени должны совпадать с backend: от 1 до 15 символов, только латинские/русские буквы, точка и подчёркивание; пробелы и цифры запрещены.

Последовательность запросов:

| Действие | Запрос | Ответ |
|---|---|---|
| Запросить SMS | `POST /api/auth/phone/request-code/`, JSON `{ "name": "Иван", "phone": "+79001234567" }` | `200`, `{ "message": "Код отправлен" }`; при `DEBUG=True` может прийти `debug_code` |
| Подтвердить SMS | `POST /api/auth/phone/verify/`, JSON `{ "phone": "+79001234567", "code": "1234" }` | `{ "access": "…", "refresh": "…", "user": {…} }` |
| Получить профиль | `GET /api/auth/me/` | Профиль текущего пользователя |
| Изменить имя | `PATCH /api/auth/me/`, JSON `{ "name": "НовоеИмя" }` | Обновлённый профиль |
| Обновить токены | `POST /api/auth/token/refresh/`, JSON `{ "refresh": "…" }` | Новые `access` и `refresh` |
| Выйти | `POST /api/auth/logout/`, JSON `{ "refresh": "…" }` | `204`; refresh-токен отзывается |

После проверки кода backend создаёт пользователя, если телефон новый, и возвращает токены вместе с объектом `user`. В `AuthContext` установи именно `response.user`, а сами токены сохрани отдельно.

Для каждого запроса после входа отправляй:

```http
Authorization: Bearer <access>
```

При истёкшем access обнови токены через refresh endpoint и повтори запрос. При ротации refresh-токена сохраняй **оба новых значения**. Для состояния входа после перезагрузки приложения нужно восстановить токены из выбранного хранилища. Cookie-сессия и CSRF-заголовок для этой схемы не нужны.

При выходе отправь текущий refresh-токен с Bearer access, затем удали оба токена из хранилища и очисти пользователя в `AuthContext`.

Ответ пользователя содержит `id`, `name`, `phone`, `createdAt` и `course` — список назначенных ему курсов. Не считай весь ответ проверки кода самим пользователем: данные пользователя лежат в `response.user`.

Код ошибки при неверном или просроченном SMS-коде:

```json
{
  "detail": "Неверный код или срок действия истёк",
  "code": "invalid_code"
}
```

## 3. Формат авторов и курсов

Backend оставляет модель `Course`, но для текущего интерфейса сериализует каждый курс как одну продаваемую публикацию. Это намеренное соответствие: **один курс — одна карточка/покупаемый материал**, а содержимое состоит из уроков.

Это не просто переименование модели. Сериализатор адаптирует поля Course к JSON-контракту Post. Такая схема не создаёт технической ошибки, пока курс целиком является одной покупаемой единицей. Если позже появятся самостоятельные статьи или продажа отдельных уроков, их нужно будет моделировать отдельно, чтобы не смешивать два разных продукта.

Список категорий:

```http
GET /api/categories/
```

Ответ — массив строк, например `Дизайн`, `Программирование`, `Финансы`.

Список публикаций:

```http
GET /api/posts/?search=django&category=Программирование&limit=10
```

Также доступны `/api/courses/` и `/api/courses/:id/`. Карточка приходит примерно в таком виде:

```json
{
  "id": 12,
  "title": "Основы Django",
  "excerpt": "Краткое описание",
  "category": "Программирование",
  "access": "paid",
  "price": "990.00",
  "publishedAt": "2026-11-13T10:00:00Z",
  "hasAccess": false,
  "creator": { "id": 3, "name": "Иван Автор" }
}
```

`price` сериализуется как десятичная строка; если компоненту нужна арифметика, преобразуй её в число на границе API-сервиса. ID из Django — числа, а не mock-строки вроде `p1` и `c1`.

Карточки авторов доступны по `/api/creators/` (совместимый адрес для фронта) и `/api/authors/`. Автор содержит `id`, `name`, `bio`, `category`, `avatar`, `postsCount`. Детальная карточка также содержит массив `posts` и `courses`.

## 4. Как получить тело материала и уроки

Детальная карточка по `/api/posts/:id/` или `/api/courses/:id/` содержит:

- `preview` — открытый фрагмент;
- `body` — массив текстов уроков, если у пользователя есть доступ; иначе `null`;
- `lessons` — список уроков с `id`, `title`, `position`, `body`.

Можно запросить уроки отдельно:

```http
GET /api/courses/:id/lessons/
GET /api/lessons/:id/
```

Текст платного курса backend не выдаёт пользователю без доступа: `body` будет `null`, `hasAccess` — `false`. Для текущего `ContentPage` массив `body` технически подходит: он перебирает его и отображает каждый элемент отдельным абзацем. Однако эта страница не покажет заголовки уроков. Если нужно показывать структуру курса, обнови её так, чтобы она отображала `lessons` по `position`, включая заголовок и текст каждого урока.

Аватар автора может приходить как URL. Для локального Django-сервера загружаемые медиа доступны через `/media/` при `DEBUG=True`.

## 5. Отдельно про оплату

Серега, пока оставь оплату в mock-режиме. Backend пока не реализует `/api/payments/`, `/api/me/payments/` и `/api/me/purchases/`; история транзакций и подтверждение платежа появятся позднее. Не переключай оплату на Django вместе с авторизацией и каталогом.

## 6. Как проверить подключение после изменений

1. Запустить Django на `localhost:8000`, Vite — на `localhost:5173`.
2. Включить API-режим отдельно для авторизации и каталога, оплату оставить mock.
3. Убедиться в Network, что запрос кода содержит и `name`, и `phone`.
4. Убедиться, что после проверки кода токены сохраняются, профиль загружается с Bearer access, а `AuthContext.user` получает объект `user`.
5. Открыть каталог, страницу автора и страницу публикации; проверить `title`, `creator`, `publishedAt`, превью и скрытие текста без доступа.

Пока Серега не закончит JWT-изменения, текущая React-авторизация с Django работать не будет: фронт ещё отправляет только телефон, ожидает сессию и не добавляет Bearer-токен.

## 7. Роли, личный кабинет автора и модерация

Серега, backend добавляет роли `user`, `author`, `moderator`, `superuser`. Роль нельзя менять запросом из профиля: её назначает администратор. Django `is_superuser` также возвращается отдельным `isSuperuser`. После входа профиль `/api/auth/me/` содержит:

```json
{
  "id": 12,
  "name": "Иван",
  "phone": "+79001234567",
  "role": "author",
  "isSuperuser": false,
  "avatar": "http://localhost:8000/media/users/avatars/avatar.jpg",
  "authorProfiles": [{ "id": 3, "name": "Иван Автор" }],
  "course": []
}
```

Используй `role` для показа разделов личного кабинета, а для административного доступа проверяй `isSuperuser`. `authorProfiles` — связанные карточки автора. У обычного пользователя список пуст. Модератор получает роль `moderator`, но не обязательно имеет доступ в Django Admin.

### Фото профиля и публикации

Профиль можно обновить через `PATCH /api/auth/me/` с Bearer JWT. Для загрузки аватара отправляй `multipart/form-data` с полем `avatar` (при необходимости вместе с `name`). Ответ профиля вернёт URL в `avatar`; пустая строка означает, что фото не установлено.

Карточки каталога `/api/posts/` и `/api/posts/:id/` теперь содержат поле `photo` — URL загруженного изображения публикации либо `null`. Покажи это изображение вместо цветного placeholder. Backend не меняет внешний вид фронтенда; расположение, размеры и fallback остаются на стороне интерфейса.

### Авторская часть личного кабинета

Для авторской вкладки используй эти запросы с `Authorization: Bearer <access>`:

| Действие | Endpoint | Результат |
|---|---|---|
| Список своих публикаций | `GET /api/author/courses/` | Все собственные материалы со статусом и комментарием модератора |
| Создать публикацию | `POST /api/author/courses/` | Создаёт курс со статусом `pending` |
| Открыть / изменить / удалить публикацию | `GET/PATCH/PUT/DELETE /api/author/courses/:id/` | Доступ только к своим курсам; любое изменение повторно отправляет курс на проверку |
| Список уроков курса | `GET /api/author/courses/:id/lessons/` | Уроки по `position`, полный текст доступен владельцу |
| Добавить урок | `POST /api/author/courses/:id/lessons/` | Создаёт урок и отправляет курс на проверку |
| Изменить / удалить урок | `PATCH/PUT/DELETE /api/author/courses/:id/lessons/:lessonId/` | Меняет только урок собственного курса и повторно ставит курс на проверку |

Пример создания курса:

```json
{
  "author_id": 3,
  "name": "Основы Django",
  "category": "programming",
  "excerpt": "Краткое описание курса",
  "preview": "Открытый фрагмент",
  "access": "paid",
  "price": "990.00"
}
```

`author_id` должен быть из `authorProfiles` текущего пользователя. Если у него ровно один связанный профиль, поле можно не передавать. Цена бесплатной публикации должна быть `0`, платной — больше нуля. После создания добавляй содержимое отдельными запросами к lesson endpoint. При изменении фото курса отправляй `multipart/form-data` с полем `photo`; при обычных JSON-запросах изображение не передаётся.

Статусы: `pending` — проверяется; `published` — опубликована; `revision` — возвращена автору на доработку; `rejected` — отклонена. В карточке автора показывай `status` и `moderator_comment`, чтобы автор видел причину возврата/отказа. Изменение курса или любого урока очищает старый комментарий и создаёт новую проверку. Непроверенные и отклонённые публикации не попадают в публичный каталог и публичную страницу автора.

### Очередь модератора

| Действие | Endpoint | JSON для решения |
|---|---|---|
| Очередь проверки | `GET /api/moderation/courses/` | Список публикаций `pending`, включая уроки |
| Одобрить | `POST /api/moderation/courses/:id/review/` | `{ "decision": "approve", "comment": "" }` |
| Отклонить | `POST /api/moderation/courses/:id/review/` | `{ "decision": "reject", "comment": "Причина" }` |
| Вернуть автору | `POST /api/moderation/courses/:id/review/` | `{ "decision": "revision", "comment": "Что исправить" }` |

Для `reject` и `revision` комментарий обязателен. После одобрения статус становится `published`, курс появляется в каталоге, авторе и публичных URL. После двух других решений автор увидит комментарий в своём списке. Запросы доступны только ролям `moderator` и `superuser`; автор не может одобрить собственный курс.

В авторском кабинете нужны вкладки «Мои публикации» и фильтры по статусам. В кабинете модератора — очередь `pending`, просмотр карточки и уроков, поле комментария и действия «Одобрить», «Отклонить», «Вернуть на доработку». После решения обновляй очередь и показывай результат пользователю.

### Какие страницы и формы нужно добавить

Серега, это отдельная часть фронтенда: backend предоставляет API и права, но самих экранов в React пока нет.

1. **Кабинет автора — список публикаций.** Добавь в профиль автора страницу/вкладку «Мои публикации». Загружай `GET /api/author/courses/`. Показывай название, категорию, цену, фото, статус и комментарий модератора. Добавь фильтры `pending`, `published`, `revision`, `rejected` и кнопку создания.
2. **Форма создания/редактирования публикации.** Поля: название, категория, краткое описание, открытый фрагмент, тип доступа, цена, фото. При нескольких `authorProfiles` дай выбрать профиль автора и передавай `author_id`. Сохраняй через `POST /api/author/courses/` или `PATCH /api/author/courses/:id/`. После сохранения покажи «Отправлено на проверку»; публикация не должна появляться в публичном каталоге до одобрения.
3. **Редактор уроков.** В форме/на странице курса показывай упорядоченные уроки и позволяй добавить, изменить, переставить и удалить уроки через вложенные endpoints `/api/author/courses/:id/lessons/`. Поля урока: заголовок, длинный текст и позиция. При каждом изменении курса статус снова станет `pending`.
4. **Экран модератора.** Добавь отдельный пункт навигации для роли `moderator` (и `isSuperuser`). Страница очереди загружает `GET /api/moderation/courses/`, показывает публикацию, автора, фото и полный список уроков. В карточке проверки нужны действия «Одобрить», «Отклонить» и «Вернуть на доработку», а для двух последних — обязательное поле комментария. Отправляй решение на `POST /api/moderation/courses/:id/review/`, затем обновляй очередь.
5. **Профиль и аватар для любой роли.** Добавь редактирование имени и загрузку аватара; отправляй `PATCH /api/auth/me/` как `multipart/form-data`. Отображай возвращённый `avatar` в шапке и профиле. Роль и список доступов пользователь в этой форме менять не может.

Не делай отдельную страницу управления ролями: назначение `author`/`moderator` выполняет администратор через Django Admin. Для обычной навигации ориентируйся на ответ профиля, а права на запросы всё равно проверяются backend.

### Подготовка аккаунтов для разработки

Назначение ролей и связей выполняется в Django Admin: в разделе Users установи роль аккаунта, затем в Author привяжи аккаунт в поле «Аккаунты авторов». Для модератора достаточно назначить роль `moderator`. Роль в браузере сама по себе никаких полномочий не даёт: каждый endpoint проверяет JWT и роль/владение на backend.

Удаление автора в Django Admin удалит его курсы и уроки; удаление курса удалит связанные уроки. Учитывай это перед подтверждением удаления.

## 8. Проверка нового API

1. После того как backend миграции будут созданы и применены, назначь тестовому аккаунту роль `author` и привяжи его к карточке автора.
2. Войди этим аккаунтом и создай курс через авторскую вкладку. Проверь, что он отображается как `pending`, но отсутствует в `/api/posts/` и публичной странице автора.
3. Добавь несколько уроков и проверь изменение статуса курса обратно на `pending`.
4. Войди аккаунтом `moderator`, открой очередь, верни материал на доработку с комментарием и проверь его отображение у автора.
5. Отправь материал повторно и одобри его; после этого он должен появиться в публичном каталоге, а фото `photo` должно отображаться в карточке.
6. Загрузи аватар через профиль и проверь, что `/api/auth/me/` возвращает URL `avatar`.
